# WitBoot 需求管理流程

[需求与设计台账](requirements.md)用于收集需求、归类、排期和记录状态。编号跨迭代保持稳定，一个需求可以通过多次变更完成。OpenSpec 变更目录保存本次的范围、验收场景、技术决策和实施任务。归档后的能力规范保存已验收的系统行为。工程约定见 [AGENTS.md](../AGENTS.md)。

首轮的 `ENV-001` 和 `ENV-002` 关联同一个变更 `establish-local-development-baseline`，验收并归档后沉淀到能力 `local-development`。以后调整同一能力时沿用能力名和原需求编号，在新的变更中描述本次调整。

## 从登记到归档

| 状态 | 进入条件 | 记录位置 |
| --- | --- | --- |
| 待梳理 | 已登记编号、能力归属与用户目标 | 需求目录 |
| 待澄清 | 已确定探索范围，仍有影响验收或兼容性的决策 | 需求状态记录，保留具体问题 |
| 待审阅 | 变更已形成可审阅的范围、场景和任务 | 需求状态记录链接到 OpenSpec 变更 |
| 待实施 | 已确认本次需求、边界和完成条件 | 变更文档 |
| 进行中 | 已开始实施，任务进度可从勾选项追踪 | `tasks.md` |
| 待验收 | 实施已完成，相关测试与检查结果已记录 | 变更中的验证任务和验收记录 |
| 已交付 | 场景验收通过，已同步规范并归档 | 需求目录链接到归档变更与主规范 |
| 已搁置 | 发现依赖阻塞，或调整优先级后暂停 | 记录原因和恢复条件 |

需求调整时按新的决定修订提案、场景、设计和任务，再继续实施。已有交付行为的新调整使用新的变更关联原需求编号。需求验收未通过时回到进行中，保留失败场景和待办。目录只在阶段发生变化时更新，任务明细由 `tasks.md` 维护。

## 每轮保留的信息

- 登记需求时记录编号、能力归属、用户目标、现状与前置依赖。预期规则未确定时，在状态记录写出具体问题。
- 提案中引用需求编号并划定本次范围。一个变更只纳入能一起验收的需求，以可观察的场景表达成功、失败和边界行为。
- 实施时按任务清单推进。涉及接口、数据或权限的行为在相应场景里验证。部分交付保留剩余场景的需求状态。
- 验收记录写明场景、环境、执行命令或操作、结果及未覆盖项。运行结果以实际执行为准，测试报告记录实际用例数。
- 归档后核对主规范和归档路径，回填需求状态与链接。主规范中的场景可继续作为后续迭代的回归依据。

## 在 Codex 中实践

1. 选定编号后用 `$openspec-explore` 讨论规则。审阅者确认可观察行为和范围，技术细节由设计说明记录。
2. 用 `$openspec-propose` 建立变更。审阅 `proposal.md`、`specs/`、`design.md` 和 `tasks.md`，需要修订时用 `$openspec-update-change`。
3. 用 `$openspec-apply-change <变更名>` 实施。中断后根据未完成任务和已有验证结果恢复。
4. 按规范逐项验收。在 PowerShell 运行 `openspec validate <变更名> --type change --strict` 检查文档结构，用项目检查和测试验证运行行为。
5. 验收后用 `$openspec-archive-change <变更名>` 同步并归档，核对已交付行为能在主规范中找到。

可用 `openspec list` 查看在途变更与任务，`openspec status --change <变更名>` 查看规划文档状态，`openspec list --specs` 查看已归档到主规范的能力。完整操作见 [OpenSpec 官方快速开始](https://openspec.dev/docs/quickstart)。

从 [当前状态与变更](requirements.md#当前状态与变更) 打开目标提案。

## 修改某个功能

从 [功能需求目录](requirements.md) 打开中文功能文件，例如 [用户管理](功能需求/用户管理.md)。按原编号登记修改原因、期望行为与待确认事项。已有在途变更时用 `$openspec-update-change` 修订其中的规范、设计和任务。调整已交付的行为时提出新变更，在增量规范中使用 `MODIFIED Requirements`，验收归档后更新主规范和功能文件中的状态与链接。

中文用于功能文件名、需求描述和场景。OpenSpec 能力路径和变更名使用英文短横线格式，例如 `user-management`。结构标题沿用项目模板。

## 已有功能的复验

1. 从台账选择一个已有功能，用源码、配置、页面和历史设计定位实际入口与待核对行为。
2. 用 OpenSpec 提案记录目标行为、设计与验证任务。对设计仍未确定的行为，在台账记录问题并在探索阶段确认。
3. 在隔离环境运行已有实现，逐项记录场景结果。通过的场景复用现有代码，未通过的场景关联修正变更并复验。
4. 验收通过后同步并归档。复验过程中的设计决策和证据与归档变更一同保留。

首个复验对象是 USR-001 用户列表。验收环境就绪后，用新工作区准备固定数据，核对关键词、翻页、删除过滤和空结果。随后用 USR-002 演练在已有行为基线上增加校验规则。
