# Design

## Context

后端由 `witboot-start` 装配。主配置默认使用 `prod`，现有 `dev` 配置为空，前端通过 `VITE_API_BASE_URL` 设置 API 地址。旧建表脚本包含删表语句，Redis 测试包含写操作。参见 [提案](proposal.md) 和 [验收场景](specs/local-development/spec.md)。

## Goals / Non-Goals

**Goals**

- 从本地配置明确解析开发和测试资源，并提供可观察的启动状态。
- 留下可在新工作区复现的启动和测试步骤。

**Non-Goals**

- 数据库版本化迁移与管理员初始化分别由 `DB-001` 和 `DB-002` 交付。
- 登录成功和业务接口行为由对应业务变更验收。

## Decisions

1. 以 `dev` 为日常启动的默认 profile，集成测试显式选择 `test`。开发和测试的 MySQL、Redis 配置使用各自的外部参数，缺项时报告缺少的配置键。生产部署显式设置 `SPRING_PROFILES_ACTIVE=prod`。这种安排沿用现有 Spring 启动方式。
2. 开发和测试使用独立的数据库与缓存。文档给出在新建隔离数据库上准备必要表的步骤，仅使用现有建表定义中的创建语句。已有数据库需要先检查实际结构，后续由版本迁移处理。
3. 用后端健康状态和前端到本地后端的连通性来验收。健康信息仅暴露运行所需的最小状态。启动说明记录实际访问路径与所需授权方式，避免把前端能打开页面误判为后端已就绪。
4. 先用项目当前的 Maven 与 pnpm 构建，记录版本、依赖准备、启动、停止、重启和验证命令。容器编排可在交付需求中单独评估。

## Risks / Trade-offs

- 旧部署可能依赖默认 `prod`。发布前检查启动配置并显式设置生产 profile。
- 测试包含持久化写入。执行前核对实际生效的数据库与缓存目标，使用隔离环境并记录报告中的实际用例数。
- 空白数据库只有结构时无法验收登录。当前使用登录页可访问和后端就绪作为验收结果，`DB-002` 完成后再验证登录。

## Migration Plan

部署配置提前声明显式生产 profile，再发布本变更。若发布验证失败，回退应用版本及相应的启动配置。开发验证复用同一个隔离数据库，重启时保留已有记录。
