# Design

## Context

[提案](proposal.md)选择复验现有用户列表。前端发送 `pageNo`、`pageSize` 和 `keyword`。后端控制器读取的页码名是 `pageNum`，持久化层也按查询对象的 `pageNo` 初始化分页。现有 Mapper 使用关键词匹配用户名或姓名，并过滤删除标识。两条分页路径的实际表现需通过同一组固定数据验证。

## Goals / Non-Goals

**Goals**

- 对照 [用户列表规范](specs/user-management/spec.md)验证 API 和管理端页面。
- 记录实际请求参数、响应和测试数据条件，使下一轮分页校验可以重跑基线。

**Non-Goals**

- 分页参数边界属于 `USR-002`。用户创建、修改和删除行为分别追踪。

## Decisions

1. 从管理端现有查询入口发起测试，同时记录实际 HTTP 请求。这样可以核对浏览器传参、后端映射和持久化查询的结果。
2. 使用隔离数据库中的固定数据，覆盖用户名匹配、姓名匹配、已删除记录以及足够触发翻页的记录。两次翻页请求之间保持数据稳定。
3. 保留场景证据和实际结果。发现差距时关联后续修正变更，待相应场景复验通过后同步有关规范。

## Risks / Trade-offs

- 双分页入口可能导致调用方与 API 的观察结果不同。分别检查浏览器请求和 API 返回，并记录实际生效的分页参数。
- 查询排序会影响翻页可复验性。记录实际排序表现和相邻页结果，发现不稳定时在台账登记修正。
- 验收依赖独立的数据库和登录凭据。使用已验收的开发环境及测试账号。
